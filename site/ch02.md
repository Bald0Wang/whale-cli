# 第 2 章 · 工具的统一管理

> 本章代码：`code/chapter-02/`。在 OpenClaw 目录下运行：`python ../code/chapter-02/main.py "列出 src/tools 下的文件，读取 index.ts"`。本章新增了 `list_dir` 工具和 Toolset 机制。

第 1 章用一个 `read_file` 跑通了最小的 Agent Loop。现在想加第二个工具——`list_dir`，让 Whale CLI 能看看目录里有什么。`list_dir` 在这一章主要是用来演示"加工具"的过程，后面真正用来探索目录结构的是 Ch05 的 Glob。函数本身几行就能写完：

```python
def list_dir(path: str = ".") -> str:
    items = sorted(Path(path).iterdir())
    return "\n".join(item.name for item in items)
```

问题是，加这个工具需要改三个地方：工具 schema 字典里加一段 JSON 描述，dispatch 函数里加一个分支，再加上函数本身。三处信息描述的是同一个工具，却散落在不同位置。现在只有两个工具，手动同步还能接受。后面 Whale CLI 要加 Write、Edit、Glob、Grep、Bash，每加一个工具都要在三处保持一致，漏掉任何一处就会出现"模型想调用但程序找不到"或"程序能执行但模型不知道"的裂缝。

这一章把工具信息收拢到一处，让"定义一个工具"变成只写一个函数。先从 `list_dir` 加不进去这个问题开始。

---

## 1. 写好了函数，不等于模型知道它存在

第 1 章调用模型时，发送的不只是 `messages`，还有一份工具清单：

```python
response = llm.chat(
    messages,
    tools=TOOLS,
)
```

`TOOLS` 中目前只有 `read_file`：

```python
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "read_file",
            "description": "读取当前项目中的文本文件。",
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {"type": "string"}
                },
                "required": ["path"],
            },
        },
    }
]
```

模型看不到 Python 源码。它不知道我们的程序里新写了一个 `list_dir()`，也不会扫描本地函数，猜测哪些可以调用。对模型来说，可用工具只有 API 请求中提供的那份清单，所以还要补上 `list_dir` 的 schema，也就是一段描述工具名称、用途和参数格式的 JSON（第 1 章 §7 定义过 `read_file` 的 schema）：

```python
{
    "type": "function",
    "function": {
        "name": "list_dir",
        "description": (
            "列出指定目录下的文件和子目录。"
            "当不知道文件的准确路径,需要先查看目录结构时使用。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "path": {
                    "type": "string",
                    "description": "要查看的目录,默认是当前目录",
                }
            },
        },
    },
}
```

加上 schema 再运行一次，终端里会看到这样的输出：

```text
⏺ list_dir({"path": "."})
  ⎿ Error: 工具 'list_dir' 不存在
```

刚才模型不知道 `list_dir`；现在模型知道了，本地程序却说它不存在。两边各执一词。

## 2. 模型返回的是字符串，程序需要的是函数

先看模型返回的内容：

```json
{
  "name": "list_dir",
  "arguments": "{\"path\":\".\"}"
}
```

这里的 `"list_dir"` 只是一个字符串。模型不知道 Whale CLI 是用 Python 写的，也没有返回某个可以直接执行的函数对象。它只是在说：

> 我希望调用名为 `list_dir` 的工具。

本地程序收到这个名字后，还要找到真正的 Python 函数：

```mermaid
flowchart LR
    A["字符串 \"list_dir\""] --> B["Python 函数 list_dir"] --> C["执行 list_dir(path=\".\")"]
```

第 1 章用一个字典保存这种对应关系：

```python
TOOL_FUNCTIONS = {
    "read_file": read_file,
}
```

执行工具时，程序先查字典：

```python
def run_tool(name, args):
    fn = TOOL_FUNCTIONS.get(name)

    if fn is None:
        return f"Error: 工具 '{name}' 不存在"

    return fn(**args)
```

现在错误原因就清楚了。我们完成了两件事：写出了 `list_dir` 函数，把 `list_dir` 的 schema 发给了模型。却漏掉了第三件事：

```python
TOOL_FUNCTIONS = {
    "read_file": read_file,
    "list_dir": list_dir,
}
```

模型选对了工具，函数本身也可以运行。缺少的是中间的连接：根据名称找到对应处理函数，再把任务交给它。工程里通常把这个过程叫作 dispatch（分发）。眼前的过程就是：

模型返回工具名，程序按名字查找函数，再把参数交给函数执行。

## 3. 一个工具被写了三遍

目前，`list_dir` 分散在三个地方。

给模型看的 schema：

```python
{
    "name": "list_dir",
    "description": "...",
    "parameters": {...},
}
```

真正执行的函数：

```python
def list_dir(path="."):
    ...
```

名字到函数的映射：

```python
"list_dir": list_dir
```

三处分别解决不同问题：

| 部分              | 谁使用  | 作用             |
| --------------- | ---- | -------------- |
| Schema          | 模型   | 判断何时调用、怎样填写参数  |
| Function        | 本地程序 | 真正执行目录读取       |
| Name → Function | 本地程序 | 把模型返回的字符串连接到函数 |

一个工具时，很难感受到问题。增加第二个工具后，我们已经碰到了两种不同步：

| 缺失的部分 | 后果 |
| --- | --- |
| 只写函数，没有 Schema | 程序会做，但模型不知道可以做 |
| 有 Schema，没有函数映射 | 模型会调用，但程序不知道怎样执行 |

还可能出现第三种情况。假设 schema 中把参数写成：

```json
{
  "directory": {
    "type": "string"
  }
}
```

函数却仍然接受：

```python
def list_dir(path="."):
    ...
```

模型会按 schema 返回：

```json
{
  "directory": "."
}
```

程序执行：

```python
list_dir(directory=".")
```

随后报错：

```text
TypeError: list_dir() got an unexpected keyword argument 'directory'
```

工具名对上了，函数也找到了，参数定义却分叉了。这些故障有一个共同根源：

> “一个工具是什么”被写在了几个相互独立的地方。

  <img src="/images/ch02/ch02-tool-defined-three-times.webp" alt="list_dir 的 Schema、Python 函数和名称映射分散在三处" loading="lazy" />

## 4. 让模型和程序读取同一张表

把三份信息收拢到一个地方。做法是：让每个工具自己携带 schema 和执行逻辑，再用一个统一的注册表管理所有工具。

先定义一个 Tool 基类——每个工具是一个类，带三个属性：`name`、`description`、`schema`，以及一个 `__call__` 方法负责真正执行：

```python
class Tool:
    name: str = “”
    description: str = “”
    schema: dict = {}

    def __call__(self, **kwargs) -> str:
        raise NotImplementedError
```

`__call__` 是 Python 的特殊方法——定义了它以后，类的实例可以像函数一样被调用：`tool(path=”.”)` 等价于 `tool.__call__(path=”.”)`。

`list_dir` 继承 Tool，把 schema 和执行逻辑写在同一个类里：

```python
class ListDirTool(Tool):
    name = “list_dir”
    description = “列出指定目录下的文件和子目录。”
    schema = {
        “type”: “function”,
        “function”: {
            “name”: “list_dir”,
            “description”: “列出指定目录下的文件和子目录。”,
            “parameters”: {
                “type”: “object”,
                “properties”: {
                    “path”: {“type”: “string”}
                },
            },
        },
    }

    def __call__(self, *, path=”.”):
        items = sorted(Path(path).iterdir())
        return “\n”.join(i.name for i in items)
```

参数前面的 `*` 表示后面的参数必须用关键字传递（`path=”.”`），不能按位置传。这和模型返回的 JSON 正好匹配——`{“path”: “.”}` 总是用键名指定参数。

现在 schema 和函数不再分开写了——它们在同一个类的定义里，改一个不会忘了另一个。

再建一个 Toolset（注册表）来管理所有工具：

```python
class Toolset:
    def __init__(self):
        self._tools = {}

    def register(self, tool: Tool):
        self._tools[tool.name] = tool

    def get(self, name: str):
        return self._tools.get(name)

    def all_schemas(self):
        return [t.schema for t in self._tools.values()]
```

注册工具：

```python
toolset = Toolset()
toolset.register(ReadFileTool())
toolset.register(ListDirTool())
```

模型需要工具清单时：

```python
tools = toolset.all_schemas()
```

执行工具时：

```python
tool = toolset.get(name)
result = tool(**args)
```

`**args` 把字典拆成关键字参数——`tool(**{"path": "."})` 等价于 `tool(path=".")`。模型返回 JSON，Python 用 `**` 解包成函数调用，中间不需要手动拆字段。

```mermaid
flowchart LR
    R[“Toolset”] --> S[“all_schemas()”] --> M[“发给模型”]
    R --> G[“get(name)”] --> L[“本地执行”]
```

只要工具没有 `register`，它既不会出现在模型的工具清单里，也不会被本地程序执行。

## 6. Toolset：管理工具注册和调度

现在，一次工具调用的路径变成了：

模型生成参数，Toolset 查找工具，再调用工具的 `__call__`。

这里有一个新的问题。模型虽然会参考 schema 生成参数，但它的输出仍然可能出错。例如 schema 规定：

```json
{
  “start_line”: {
    “type”: “integer”
  }
}
```

模型却返回：

```json
{
  “start_line”: “20”
}
```

Toolset 如果直接执行：

```python
tool = toolset.get(“read_file”)
tool(path=”main.py”, start_line=”20”)
```

错误可能一直到 `__call__` 内部才出现：

```text
TypeError: unsupported operand type(s) for -: 'str' and 'int'
```

这条错误是写给 Python 开发者看的。模型更需要看到的是：

```text
参数 'start_line' 应为 integer,实际收到 string
```

Schema 只能告诉模型”应该怎样传”。本地程序仍然要检查”实际上怎样传”。Toolset 正好位于模型输出进入工具执行的入口，因此参数校验也适合放在这里。先检查必填参数：

```python
def _validate_args(args, schema):
    parameters = schema[“function”][“parameters”]
    required = parameters.get(“required”, [])

    for field in required:
        if field not in args:
            return f”缺少必需参数 '{field}'”
```

再检查未知参数和基本类型：

```python
    properties = parameters.get(“properties”, {})

    for field, value in args.items():
        definition = properties.get(field)

        if definition is None:
            return f”未知参数 '{field}'”

        expected = definition.get(“type”)

        if expected == “string” and not isinstance(value, str):
            return f”参数 '{field}' 应为 string”

        if expected == “integer” and not isinstance(value, int):
            return f”参数 '{field}' 应为 integer”

    return None
```

把校验逻辑放到 Toolset 的 `run` 方法里，执行工具前先经过这道检查：

```python
class Toolset:
    # ... register / get / all_schemas 同前 ...

    def run(self, name: str, args: dict) -> str:
        tool = self._tools.get(name)

        if tool is None:
            available = “, “.join(self._tools.keys())
            return (
                f”Error: 工具 '{name}' 不存在。”
                f”当前可用工具:{available}”
            )

        error = _validate_args(args, tool.schema)

        if error:
            return f”Error: {name} 参数校验失败:{error}”

        try:
            result = tool(**args)
            return result if isinstance(result, str) else str(result)
        except Exception as exc:
            return (
                f”Error: {name} 执行失败:”
                f”{type(exc).__name__}: {exc}”
            )
```

现在模型传错参数时，Agent Loop 不会直接崩溃。错误会作为工具结果回到模型：

```text
Error: read_file 参数校验失败:
参数 'start_line' 应为 integer
```

模型下一轮可以修正参数，再调用一次。加上参数校验后，Toolset 同时负责工具清单生成、名称到工具对象的查找、以及入口处的类型检查。

## 7. 完整的 Tool 基类与 Toolset

```python
# registry.py

from typing import Any


class Tool:
    """工具基类:每个工具继承它,带上 schema 和执行逻辑。"""

    name: str = ""
    description: str = ""
    schema: dict = {}

    def __call__(self, **kwargs) -> str:
        raise NotImplementedError


def _validate_args(
    args: dict,
    schema: dict,
) -> str | None:
    parameters = schema["function"]["parameters"]
    properties = parameters.get("properties", {})
    required = parameters.get("required", [])

    for field in required:
        if field not in args:
            return f"缺少必需参数 '{field}'"

    for field, value in args.items():
        definition = properties.get(field)

        if definition is None:
            available = ", ".join(properties.keys())
            return (
                f"未知参数 '{field}'。"
                f"可用参数:{available}"
            )

        expected = definition.get("type")

        if expected == "string" and not isinstance(value, str):
            return f"参数 '{field}' 应为 string"

        if expected == "integer" and not isinstance(value, int):
            return f"参数 '{field}' 应为 integer"

        if expected == "boolean" and not isinstance(value, bool):
            return f"参数 '{field}' 应为 boolean"

    return None


class Toolset:
    """工具注册表:管理所有工具的注册、查找和执行。"""

    def __init__(self):
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool):
        if tool.name in self._tools:
            raise ValueError(f"工具名重复注册:{tool.name}")
        self._tools[tool.name] = tool

    def get(self, name: str) -> Tool | None:
        return self._tools.get(name)

    def all_schemas(self) -> list[dict]:
        return [t.schema for t in self._tools.values()]

    def run(self, name: str, args: dict) -> str:
        tool = self._tools.get(name)

        if tool is None:
            available = ", ".join(self._tools.keys())
            return (
                f"Error: 工具 '{name}' 不存在。"
                f"当前可用工具:{available}"
            )

        error = _validate_args(args, tool.schema)

        if error:
            return f"Error: {name} 参数校验失败:{error}"

        try:
            result = tool(**args)
            return result if isinstance(result, str) else str(result)
        except Exception as exc:
            return (
                f"Error: {name} 执行失败:"
                f"{type(exc).__name__}: {exc}"
            )
```

工具定义集中在 `tools.py`，每个工具是一个继承 Tool 的类：

```python
# tools.py

from pathlib import Path

from registry import Tool


class ReadFileTool(Tool):
    name = "read_file"
    description = (
        "读取当前项目中的 UTF-8 文本文件。"
        "当回答问题需要知道文件内容时使用。"
    )
    schema = {
        "type": "function",
        "function": {
            "name": "read_file",
            "description": (
                "读取当前项目中的 UTF-8 文本文件。"
                "当回答问题需要知道文件内容时使用。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {
                        "type": "string",
                        "description": "要读取的文件路径",
                    }
                },
                "required": ["path"],
            },
        },
    }

    def __call__(self, *, path: str) -> str:
        try:
            return Path(path).read_text(encoding="utf-8")
        except Exception as exc:
            return f"Error: {type(exc).__name__}: {exc}"


class ListDirTool(Tool):
    name = "list_dir"
    description = (
        "列出指定目录下的文件和子目录。"
        "当不知道文件路径,需要先查看目录结构时使用。"
    )
    schema = {
        "type": "function",
        "function": {
            "name": "list_dir",
            "description": (
                "列出指定目录下的文件和子目录。"
                "当不知道文件路径,需要先查看目录结构时使用。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {
                        "type": "string",
                        "description": "要查看的目录,默认是当前目录",
                    }
                },
            },
        },
    }

    def __call__(self, *, path: str = ".") -> str:
        try:
            items = sorted(Path(path).iterdir())
        except Exception as exc:
            return f"Error: {type(exc).__name__}: {exc}"

        return "\n".join(
            item.name + ("/" if item.is_dir() else "")
            for item in items
        )
```

主程序导入工具类，创建 Toolset 并注册：

```python
from registry import Toolset
from tools import ReadFileTool, ListDirTool

toolset = Toolset()
toolset.register(ReadFileTool())
toolset.register(ListDirTool())
```

调用模型时：

```python
response = llm.chat(
    messages,
    tools=toolset.all_schemas(),
)
```

执行工具时：

```python
result = toolset.run(name, args)
```

Agent Loop 本身不需要知道系统中有几个工具。以后增加 `WriteFileTool`、`GrepTool` 或 `BashTool`，只需要写一个新类再 `toolset.register()`，主循环不用改。

调用顺序（先 `list_dir`，再 `read_file`，最后回答）不是 Toolset 决定的。Toolset 只保证：

- 模型看到的工具，程序确实能够执行
- 模型给出的参数，在进入工具前会被检查

具体选择哪个工具，仍然由模型根据当前任务和上一次工具结果决定。

只修改 `list_dir` 的 description，模型的选择也可能改变：

```text
“处理目录”
```

边界很模糊。改成：

```text
“列出指定目录下的文件和子目录。
当不知道文件的准确路径,需要先查看目录结构时使用。”
```

模型更容易判断它与 `read_file` 的分工。description 写得越精确，模型在多个工具之间选错的概率越低。

## 9. 这和常见的 Agent Demo 有什么不同

很多最小 Demo 会这样写：

```python
if name == "read_file":
    result = read_file(**args)
elif name == "list_dir":
    result = list_dir(**args)
```

只有两个工具时，这完全可以工作。如果目标只是展示”模型会调用函数”，甚至是最容易看懂的写法。但 Whale CLI 后面还会加入：

```text
Read
Write
Edit
Glob
Grep
Bash
TodoWrite
WebFetch
Task
……
```

工具增加以后，系统要处理的问题远不止”调用哪个函数”：

* 模型能看到哪些工具；
* 每个工具的参数怎样描述；
* 名称怎样对应工具对象；
* 参数进入工具前怎样校验；
* 工具是否只读；
* 是否需要我们批准；
* 能不能并发执行；
* 错误怎样返回模型；
* 动态工具怎样加入或移除。

工具数量从两个增长到十几个时，这些问题都需要一个统一的注册和查询机制来支撑，Toolset 就是这个机制。

## 10. 终端里怎么分清谁是谁

回头看 §8 跑出来的 trace。两个工具调用、两段结果、一段最终回答，全挤在一起：

```
⏺ list_dir({"path": "src/tools"})
availability.test.ts
availability.ts
descriptors.ts
execution.ts
index.ts
⏺ read_file({"path": "src/tools/index.ts"})
/**
 * Public barrel for descriptor-driven tool planning.
 */
export { evaluateToolAvailability } from "./availability.js"；
...
src/tools/index.ts 导出了 evaluateToolAvailability、formatToolExecutorRef 等函数。
```

盯三秒才分清哪行是工具调用、哪行是结果、哪行是模型回答。现在只有两个工具，后面加到七个，每个工具还可能返回几十行内容，纯文本根本没法看。我们这里用 [Rich](https://github.com/Textualize/rich) 给终端输出加一层颜色：

```python
# rich_output.py

from rich.console import Console

console = Console()

def print_tool_call(name: str, args: dict) -> None:
    args_str = ", ".join(
        f'{k}="{v}"' if isinstance(v, str) else f"{k}={v}"
        for k, v in args.items()
    )
    console.print(f"[green]⏺ {name}[/green]([cyan]{args_str}[/cyan])")

def print_tool_result(result: str, max_lines: int = 15) -> None:
    lines = result.splitlines()
    preview = "\n    ".join(lines[:max_lines])
    console.print(f"[dim]  ⎿ {preview}[/dim]")
    if len(lines) > max_lines:
        console.print(f"[dim]    ... ({len(lines) - max_lines} more lines)[/dim]")

def print_agent_answer(text: str) -> None:
    console.print(f"\n{text}")

def print_tool_error(error: str) -> None:
    console.print(f"[red]  ⎿ {error}[/red]")
```

在主循环里，工具调用和结果的 `print` 换成这些函数：

```python
from rich_output import print_tool_call, print_tool_result, print_agent_answer

# 执行工具时
print_tool_call(name, args)
result = toolset.run(name, args)
if result.startswith("Error"):
    print_tool_error(result)
else:
    print_tool_result(result)

# 最终回答时
print_agent_answer(response.get("content", ""))
```

加完以后，同样的 trace 变成：

```
⏺ list_dir(path="src/tools")                      ← 绿色
  ⎿ availability.test.ts                           ← 灰色
    availability.ts
    descriptors.ts
    execution.ts
    index.ts
    ...

⏺ read_file(path="src/tools/index.ts")            ← 绿色
  ⎿ export { evaluateToolAvailability } from ...   ← 灰色
    export { formatToolExecutorRef } from ...

src/tools/index.ts 导出了 evaluateToolAvailability 等函数。   ← 白色
```


工具名绿色、结果灰色缩进、回答白色。扫一眼就知道哪步调了什么工具。错误会显示红色，后面章节 Edit 失败时会用到。

## 11. 工具管好了，工具本身呢

到这里，Whale CLI 已经有了一套统一的工具入口：Tool 基类定义工具，Toolset 注册并管理，`all_schemas()` 生成清单，`run()` 查找并执行。以后加新工具只需要写一个类再 `toolset.register()`，schema、dispatch 和校验全部自动处理。

但 Toolset 解决的是"怎么管理工具"，工具本身够不够用是另一个问题。拿 `read_file` 去读一个近三千行的大文件，整个文件一次性进了上下文。它该返回整个文件还是一部分？该带行号吗？碰到二进制文件怎么办？下一章来解决。
