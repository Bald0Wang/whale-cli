# 第 4 章 · 写文件：Write 与 Edit

> 本章代码：`code/chapter-04/`。运行示例：`python ../code/chapter-04/main.py "读取 src/tools/execution.ts，把冒号分隔符改成斜杠"`。本章新增 Write（创建文件）和 Edit（局部替换）两个工具。

上一章结尾说到：模型读完 `execution.ts`，告诉你第 8 行的冒号可以改成斜杠。然后呢？建议停在终端里，磁盘上的文件纹丝不动。

Whale CLI 能读、能看，但不能改。要让它真正动手修改 OpenClaw 的代码，需要写文件的能力。但”写文件”至少包含两种很不一样的任务：

```text
新建 docs/contributing.md        ← 文件原来不存在，需要完整内容

把 execution.ts 里的一行代码改掉  ← 文件已经存在，只希望局部变化
```

第一种需要模型提供完整内容。第二种只希望改一小段，其余代码必须原样保留。本章实现两个工具：Write 负责创建新文件或整体替换，Edit 负责精确的局部修改。

---

## 1. Write 和 Edit 分别适合什么任务

先看两个具体请求。

### 创建一个新文件

```text
> 新建 docs/contributing.md，
> 写清楚怎样参与 OpenClaw 的开发和贡献。
```

文件原本不存在。模型只需要决定文件保存在哪里、文件中完整地写什么。这适合使用 Write。

### 修改已有文件的一行

```text
> 把 execution.ts 里执行器引用的格式化标签
> 的分隔符从 `:` 改成 `/`。
```

文件已经存在，只有 26 行。我们只希望其中几行发生变化，其他 import、函数、注释和格式都应该保留。这更适合使用 Edit。

两种工具表达的是两种不同的修改意图：

```text
Write
“请让整个文件最终变成下面这样。”

Edit
“请把当前文件中的这一段，换成另一段。”
```

Write 先来。

## 2. Write：把完整内容写入文件

一个最小的 Write 工具只需要两个参数：

```text
path
content
```

模型调用：

```json
{
  "name": "write_file",
  "arguments": {
    "path": "docs/contributing.md",
    "content": "# Contributing\n\n运行 `pnpm install` 安装依赖，再运行 `pnpm dev` 启动开发环境。\n"
  }
}
```

本地实现也很短：

```python
from pathlib import Path


def write_file(path: str, content: str) -> str:
    file_path = Path(path)

    file_path.parent.mkdir(
        parents=True,
        exist_ok=True,
    )

    file_path.write_text(
        content,
        encoding="utf-8",
    )

    return (
        f"Wrote {len(content)} characters "
        f"to {path}"
    )
```

如果 `docs/` 还不存在，先创建父目录，再把完整内容写进去。对于新文件，这种接口非常自然：

```mermaid
flowchart LR
    A["模型生成 完整内容"] --> B["Write 创建文件"] --> C["文件内容与模型 提供的一致"]
```

问题出现在已有文件上。

## 3. 用 Write 改一行代码会怎样

现在让模型完成这个任务：

```text
> 把 execution.ts 里执行器引用的格式化标签
> 的分隔符从 `:` 改成 `/`。
```

假设 `execution.ts` 有 26 行。如果系统只有 Write，模型必须先读取整个文件，再重新输出修改后的完整版本：

```json
{
  "name": "write_file",
  "arguments": {
    "path": "src/tools/execution.ts",
    "content": "这里是修改后的完整 26 行文件……"
  }
}
```

真正需要变化的可能只有几行：

```diff
- return `core:${ref.executorId}`;
+ return `core/${ref.executorId}`;
```

剩下的行，模型仍然要重新生成。这不仅浪费输出 token，还扩大了修改范围。假设原文件开头是：

```typescript
import { ToolExecutorRef } from "./types";
import { validateRef } from "./validation";
import { logger } from "../logging";
```

模型重写整个文件时，正确修改了分隔符，却漏掉了一个 import：

```diff
  import { ToolExecutorRef } from "./types";
- import { validateRef } from "./validation";
  import { logger } from "../logging";
```

从 Write 工具的角度看，这次执行是成功的。模型提供了一份完整文件，工具也将这份内容完整写入了磁盘。Write 没有"我们原本只想改几行"这个信息，也没有"其余行必须保持原样"这条约束。

模型偶尔漏代码只是表象。Write 给出的修改范围比真实意图大得多：

```text
我们的意图
只修改一行

Write 的权限
替换整个文件
```

任务只涉及局部变化时，工具应该能明确表示”只改这一处”。

## 4. Edit：用旧内容定位局部修改

局部修改不需要模型重新输出整个文件。模型只需要提供文件中现在存在的内容，以及希望替换成的新内容。工具调用可以写成：

```json
{
  "name": "edit_file",
  "arguments": {
    "path": "src/tools/execution.ts",
    "old_string": "return `core:${ref.executorId}`;",
    "new_string": "return `core/${ref.executorId}`;"
  }
}
```

最小实现可以直接使用 `str.replace()`：

```python
from pathlib import Path


def edit_file(
    path: str,
    old_string: str,
    new_string: str,
) -> str:
    file_path = Path(path)
    text = file_path.read_text(
        encoding="utf-8",
    )

    new_text = text.replace(
        old_string,
        new_string,
        1,
    )

    file_path.write_text(
        new_text,
        encoding="utf-8",
    )

    return f"Applied edit to {path}"
```

文件中没有被匹配到的部分，工具完全不碰。

Write 与 Edit 的区别：

```text
Write
完整内容覆盖

Edit
局部内容替换
```

但上面这个最小版还不安全。

## 5. 为什么 `old_string` 必须精确且只匹配一次

### 一次都没有匹配到

假设文件中的真实内容是：

```typescript
return `core.${ref.executorId}`;
```

模型却提交：

```json
{
  "old_string": "return `core:${ref.executorId}`;",
  "new_string": "return `core/${ref.executorId}`;"
}
```

Python 执行：

```python
text.replace(
    old_string,
    new_string,
    1,
)
```

找不到目标时，`str.replace()` 不会报错，它会直接返回原字符串。如果工具继续写盘并回复：

```text
Applied edit to src/tools/execution.ts
```

模型会认为修改已经成功，但文件实际上没有任何变化。所以落盘前必须先计算匹配次数：

```python
count = text.count(old_string)
```

零次匹配时拒绝修改：

```python
if count == 0:
    return (
        f"Error: old_string was not found "
        f"in {path}"
    )
```

### 匹配到多处

再看一个文件：

```typescript
function formatToolExecutorRef(ref) {
    return `core:${ref.executorId}`;
}


function formatChannelRef(ref) {
    return `core:${ref.channelId}`;
}
```

模型想修改第一个函数，却只传入：

```json
{
  "old_string": "return `core:${ref.",
  "new_string": "return `core/${ref."
}
```

`return \`core:${ref.` 出现了两次，工具不知道应该修改哪一个。它可以默认修改第一处、默认修改最后一处，或者把两处全部修改，但每一种选择都可能悄悄改错代码。因此多处匹配也要拒绝：

```python
if count > 1:
    return (
        f"Error: old_string matched "
        f"{count} locations in {path}. "
        "Include more surrounding context "
        "to make the match unique."
    )
```

模型可以扩大 `old_string` 的范围：

```json
{
  "old_string": "function formatToolExecutorRef(ref) {\n    return `core:${ref.executorId}`;",
  "new_string": "function formatToolExecutorRef(ref) {\n    return `core/${ref.executorId}`;"
}
```

这段内容只出现一次，修改目标就明确了。Edit 的核心约束由此确定：

```text
0 次匹配
文件当前内容和模型描述不一致，拒绝修改

1 次匹配
目标明确，可以修改

2 次及以上
目标有歧义，拒绝猜测
```

工具不是尽最大努力找一个差不多的位置。真正写盘之前，它必须确定目标是唯一的。

## 6. 为什么 Edit 不直接使用行号

第 3 章的 Read 已经会返回行号：

```text
   5  export function formatToolExecutorRef(ref: ToolExecutorRef): string {
   6    switch (ref.kind) {
   7      case "core":
   8        return `core:${ref.executorId}`;
```

既然模型知道目标位于第 8 行，Edit 为什么不设计成：

```json
{
  "path": "src/tools/execution.ts",
  "line": 8,
  "content": "return `core/${ref.executorId}`;"
}
```

因为行号很容易变化。假设模型准备执行两次修改，第一次在文件开头增加了五行 import，原来的第 8 行现在已经变成第 13 行。如果第二次 Edit 仍然使用旧行号，就可能修改到完全不同的代码。内容片段相对稳定——即使文件前面插入了新代码，只要：

```typescript
return `core:${ref.executorId}`;
```

仍然存在并且只出现一次，Edit 就能找到它。

因此 Read 返回的行号和 Edit 使用的 `old_string` 分别解决不同问题：

```text
行号
帮助模型理解代码位置、查看上下文

old_string
在当前文件内容中定位修改目标
```

行号适合观察，字符串内容更适合作为实际修改时的锚点。

## 7. Edit 失败后，怎样帮助模型重新定位

<figure class="chapter-figure">
  <img src="/images/ch04/ch04-edit-failure-evidence.webp" alt="Whale CLI 观察 Edit 匹配失败并据此进行下一次精确修改" loading="lazy" />
  <figcaption><strong>第 4 章 · 匹配失败：读回附近代码再改</strong>：错误结果带上当前文件片段，下一轮就有依据重新构造 <code>old_string</code>。</figcaption>
</figure>

唯一匹配阻止了错误写入，但只返回 `Error: old_string not found` 还不够。假设文件中的真实代码是：

```typescript
export function formatToolExecutorRef(ref: ToolExecutorRef): string {
    return `core.${ref.executorId}`;
```

模型却记成：

```json
{
  "old_string": "return `core:${ref.executorId}`;",
  "new_string": "return `core/${ref.executorId}`;"
}
```

它收到 `not found` 后并不知道自己错在哪里，可能开始猜测模板字符串的写法：

```text
return `core: ${ref.executorId}`;
return 'core:' + ref.executorId;
return `core:${ref. executorId}`;
```

这些尝试都不会成功，因为真实代码使用的分隔符是 `.` 而不是 `:`。工具应该把模型带回文件当前的真实状态。一种办法是寻找文件中较相似的代码，只把结果用于错误提示：

```python
import difflib


def find_closest_excerpt(
    text: str,
    old_string: str,
) -> str | None:
    file_lines = text.splitlines()
    target = old_string.splitlines()[0].strip()

    normalized = [
        line.strip()
        for line in file_lines
    ]

    # cutoff 是相似度阈值（0-1），默认 0.6。
    # 设成 0.35 是因为模型经常记错缩进或漏掉几个字符，
    # 阈值太高会找不到候选位置。
    matches = difflib.get_close_matches(
        target,
        normalized,
        n=1,
        cutoff=0.35,
    )

    if not matches:
        return None

    matched = matches[0]
    index = normalized.index(matched)

    start = max(0, index - 2)
    end = min(
        len(file_lines),
        index + 3,
    )

    return "\n".join(
        f"{line_no + 1:>5}  "
        f"{file_lines[line_no]}"
        for line_no in range(start, end)
    )
```

零匹配时：

```python
if count == 0:
    excerpt = find_closest_excerpt(
        text,
        old_string,
    )

    message = (
        f"Error: old_string was not found "
        f"in {path}."
    )

    if excerpt:
        message += (
            "\nA similar area in the current file is:\n"
            + excerpt
        )

    return message
```

模型现在得到：

```text
Error: old_string was not found
in src/tools/execution.ts.

A similar area in the current file is:
    5  export function formatToolExecutorRef(ref: ToolExecutorRef): string {
    6    switch (ref.kind) {
    7      case "core":
    8        return `core.${ref.executorId}`;
```

下一轮，它就可以根据真实内容重新构造 Edit：

```json
{
  "old_string": "return `core.${ref.executorId}`;",
  "new_string": "return `core/${ref.executorId}`;"
}
```

相似度匹配只用于帮模型找到可能相关的位置，真正修改仍然要求精确且唯一。工具可以提示"你可能记错了，文件里有一段相似内容"，却不能自行判断"那我就直接修改这段"。

"找不到 old_string 之后怎么办"，六个仓库的做法有些差别。

先说清楚下面表里的"匹配几级"是什么意思。精确匹配失败之后，有的工具直接报错，有的会放宽条件再找一遍——比如把行尾空格抹掉再比一次，还找不到就再放宽一点。试几轮就算几级。级数越多，模型抄错一点也能救回来，代价是有可能改到不该改的地方。

| | 匹配几级 | 每一级放宽了什么 | 找不到时丢回给模型什么 |
|---|---|---|---|
| Kimi CLI | 1 | —— | `No replacements were made.` |
| Whale CLI | 1 | —— | 最接近的 5 行片段 |
| Pi Agent | 2 | 尾空格、智能引号、Unicode 破折号 | 一句"请提供更多上下文" |
| Claude Code | 4 | 引号 → Tab/空格 → 两者组合 | 报错 + 把原串还给它 |
| Codex | 4 | `trim_end` → `trim` → Unicode 符号 | 原样退回它没找到的那几行 |
| Gemini CLI | 4 + LLM | 逐行去空白 → 按符号拆开、中间允许有空白 → 算相似度 → 叫模型重写 | 一段写好了排查步骤的说明 |

六家里有三家做到四级，级数一样。

放宽的东西不一样。Claude Code 处理的是引号和 Tab；Codex 处理的是破折号和几种宽度的空格（`seek_sequence.rs:76-107` 的 `normalise()` 把 em dash、en dash、花引号、多种 Unicode 空格统一）。各家兜的差异类型，大致对应各自模型常出的错。

Gemini CLI 的级数最多，容忍度写成了具体数字（都在 `gemini-cli/packages/core/src/tools/edit.ts`）：

- 编辑距离阈值 `FUZZY_MATCH_THRESHOLD = 0.1`（第 70 行）——差异在 10% 以内就认
- 空白惩罚系数 `WHITESPACE_PENALTY_FACTOR = 0.1`（第 71 行），空白上的差异只按十分之一计权——缩进错了几乎不算错，实质字符错了才算
- `old_string` 短于 10 个字符不做模糊匹配（第 1354 行），短串容易撞上不相干的位置
- `行数 × 长度²` 超过 4 亿就放弃（第 1373 行）

四级都失败之后，才调另一次模型把错误信息喂回去，让它重写 old/new（第 787 行 `attemptSelfCorrection`）。规则能解决的不花 token。

Gemini 的错误信息分两份。给人看的一句 `Failed to edit, could not find the string to replace.`，给模型看的那份（`raw`，第 370 行）是：

> `Failed to edit, 0 occurrences found for old_string in {file_path}. Ensure you're not escaping content incorrectly and check whitespace, indentation, and context. Use read_file tool to verify.`

后面这份把排查步骤写进去了：先查转义，再查空白和缩进，还不行就用 read_file 重看一遍。

`logEditStrategy` 埋点（`telemetry/loggers.ts:666`）只有一个字段 `strategy`，值是 `exact / flexible / regex / fuzzy`。他们在线上统计每次编辑是第几级完成的。有了这个分布，要不要加第五级就有依据。

## 8. 多处匹配时，把位置告诉模型

如果 `old_string` 出现了多次，只返回：

```text
Error: matched 3 locations
```

模型仍然不知道这三处分别在哪里。工具已经扫描过文件，可以顺便返回每一处的起始行号：

```python
def find_match_lines(
    text: str,
    old_string: str,
) -> list[int]:
    locations = []
    start = 0

    while True:
        index = text.find(
            old_string,
            start,
        )

        if index == -1:
            break

        line_no = (
            text.count("\n", 0, index)
            + 1
        )

        locations.append(line_no)
        start = index + 1

    return locations
```

多处匹配时：

```python
if count > 1:
    locations = find_match_lines(
        text,
        old_string,
    )

    values = ", ".join(
        str(line)
        for line in locations[:10]
    )

    return (
        f"Error: old_string matched "
        f"{count} locations in {path}. "
        f"Starting lines: {values}. "
        "Include more surrounding context "
        "to make the match unique."
    )
```

模型看到：

```text
Error: old_string matched 2 locations
in src/tools/execution.ts.

Starting lines: 8, 18.

Include more surrounding context
to make the match unique.
```

它可以重新读取第 8 行或第 18 行附近的代码，再提交更完整的 `old_string`。工具没有替模型决定改哪一处，它只是减少了模型下一轮需要重新搜索的范围。

## 9. Write 和 Edit 怎样安全地写入磁盘

Write 和 Edit 最终都需要执行：

```python
file_path.write_text(
    new_content,
    encoding="utf-8",
)
```

大多数情况下，这可以正常工作。但写盘不是一个瞬间完成的动作。如果进程在写到一半时被终止，原文件可能只剩下半截内容。对代码文件来说，这比改错一行更严重：整个文件可能无法解析。更稳妥的办法是：

```mermaid
flowchart LR
    A["写入同目录 临时文件"] --> B["确认内容 完整写入"] --> C["rename 覆盖 目标文件"]
```

```python
import os
import tempfile
from pathlib import Path


def atomic_write_text(
    path: Path,
    content: str,
) -> None:
    path.parent.mkdir(
        parents=True,
        exist_ok=True,
    )

    fd, temp_name = tempfile.mkstemp(
        dir=path.parent,
        prefix=f".{path.name}.",
        suffix=".tmp",
    )

    temp_path = Path(temp_name)

    try:
        with os.fdopen(
            fd,
            "w",
            encoding="utf-8",
        ) as file:
            file.write(content)
            file.flush()
            os.fsync(file.fileno())

        os.replace(
            temp_path,
            path,
        )

    except Exception:
        temp_path.unlink(
            missing_ok=True,
        )
        raise
```

目标文件最终只会处于两种状态：原来的完整版本，或新的完整版本，不会留下只写了一半的文件。Write 和 Edit 的上层逻辑不同：

```text
Write
模型直接提供完整的新内容

Edit
程序根据 old_string 和 new_string
计算出完整的新内容
```

但它们最终共用同一个落盘函数：

```text
Write ──┐
        ├── atomic_write_text()
Edit ───┘
```

上层工具负责决定”新文件内容是什么”，底层函数负责保证”内容怎样可靠地进入磁盘”。

## 10. Write 默认不覆盖已有文件

Write 能替换整个文件，因此默认行为应该比创建新文件更谨慎。如果目标文件已经存在，可以先拒绝：

```text
Error: src/tools/execution.ts already exists.

Use edit_file for local changes.
Set overwrite=true only when replacing
the entire file intentionally.
```

给 Write 增加一个显式参数：

```python
def write_file(
    path: str,
    content: str,
    overwrite: bool = False,
) -> str:
    ...
```

如果文件存在但没有设置 `overwrite=true`：

```python
if file_path.exists() and not overwrite:
    return (
        f"Error: {path} already exists. "
        "Use edit_file for local changes, "
        "or set overwrite=true to replace "
        "the entire file."
    )
```

于是两种行为被明确区分：

```text
创建新文件
Write 默认允许

局部修改已有文件
使用 Edit

有意替换整个已有文件
Write + overwrite=true
```

工具接口可以引导模型优先选择修改范围更小的操作。

## 11. 把 Write 和 Edit 注册成工具

前面为了讲清逻辑，用的是独立函数。注册成工具时需要包装成第 2 章引入的 Tool 类——补上 schema（告诉模型工具有哪些参数）和完整的错误处理。

### Write 工具

```python
# tools.py（WriteFileTool）

from pathlib import Path

from registry import Tool, ok, err
from file_utils import (
    atomic_write_text,
)


class WriteFileTool(Tool):
    name = "write_file"
    description = (
        "创建新的 UTF-8 文本文件，"
        "或有意替换整个文件。"
        "局部修改已有文件时应使用 edit_file。"
        "覆盖已有文件必须设置 overwrite=true。"
    )
    schema = {
        "type": "function",
        "function": {
            "name": "write_file",
            "description": (
                "创建新的 UTF-8 文本文件，"
                "或有意替换整个文件。"
                "局部修改已有文件时应使用 edit_file。"
                "覆盖已有文件必须设置 overwrite=true。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {
                        "type": "string",
                        "description": "目标文件路径",
                    },
                    "content": {
                        "type": "string",
                        "description": "文件的完整新内容",
                    },
                    "overwrite": {
                        "type": "boolean",
                        "description": (
                            "是否允许覆盖已有文件，"
                            "默认是 false"
                        ),
                    },
                },
                "required": [
                    "path",
                    "content",
                ],
            },
        },
    }

    def __call__(
        self,
        *,
        path: str,
        content: str,
        overwrite: bool = False,
    ) -> dict:
        file_path = Path(path)
        existed_before = file_path.exists()

        if existed_before:
            if not file_path.is_file():
                return err(
                    f"{path} 不是普通文件。"
                )

            if not overwrite:
                return err(
                    f"{path} 已经存在。"
                    "局部修改请使用 edit_file；"
                    "如果确实要替换整个文件，"
                    "请设置 overwrite=true。"
                )

        try:
            atomic_write_text(
                file_path,
                content,
            )
        except Exception as exc:
            return err(
                f"写入 {path} 失败："
                f"{type(exc).__name__}: {exc}"
            )

        action = (
            "Replaced"
            if existed_before
            else "Created"
        )

        return ok(
            f"{action} {path}: "
            f"{len(content)} characters",
            changed_files=[path],
        )
```

`changed_files` 记录这次调用修改了哪些文件。目前只是把路径带在返回值里，后面章节会用它在终端标注哪些文件被改动过。

### Edit 工具

```python
# tools.py（EditFileTool）

from pathlib import Path

from registry import Tool, ok, err
from file_utils import (
    atomic_write_text,
)


class EditFileTool(Tool):
    name = "edit_file"
    description = (
        "在已有 UTF-8 文本文件中执行局部替换。"
        "old_string 必须与当前文件精确匹配，"
        "并且只能出现一次。"
        "请从最近一次 Read 的结果中复制准确内容，"
        "并包含足够上下文使匹配唯一。"
    )
    schema = {
        "type": "function",
        "function": {
            "name": "edit_file",
            "description": (
                "在已有 UTF-8 文本文件中执行局部替换。"
                "old_string 必须与当前文件精确匹配，"
                "并且只能出现一次。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {
                        "type": "string",
                        "description": "要修改的文件路径",
                    },
                    "old_string": {
                        "type": "string",
                        "description": (
                            "文件中当前存在的原始内容；"
                            "必须精确且唯一"
                        ),
                    },
                    "new_string": {
                        "type": "string",
                        "description": "替换后的新内容",
                    },
                },
                "required": [
                    "path",
                    "old_string",
                    "new_string",
                ],
            },
        },
    }

    def __call__(
        self,
        *,
        path: str,
        old_string: str,
        new_string: str,
    ) -> dict:
        file_path = Path(path)

        if not file_path.exists():
            return err(
                f"文件不存在：{path}"
            )

        if not file_path.is_file():
            return err(
                f"{path} 不是普通文件"
            )

        try:
            text = file_path.read_text(
                encoding="utf-8",
            )
        except UnicodeDecodeError:
            return err(
                f"{path} 不是 UTF-8 文本，"
                "不能使用 edit_file 修改。"
            )

        count = text.count(old_string)

        if count == 0:
            excerpt = find_closest_excerpt(
                text,
                old_string,
            )

            message = (
                f"old_string 在 {path} "
                "中未找到。"
            )

            if excerpt:
                message += (
                    "\n当前文件中较接近的位置：\n"
                    + excerpt
                )

            return err(message)

        if count > 1:
            locations = find_match_lines(
                text,
                old_string,
            )

            values = ", ".join(
                str(line)
                for line in locations[:10]
            )

            return err(
                f"old_string 在 {path} "
                f"中匹配到 {count} 处。"
                f"起始行：{values}。"
                "请加入更多上下文，使匹配唯一。"
            )

        new_text = text.replace(
            old_string,
            new_string,
            1,
        )

        try:
            atomic_write_text(
                file_path,
                new_text,
            )
        except Exception as exc:
            return err(
                f"修改 {path} 失败："
                f"{type(exc).__name__}: {exc}"
            )

        old_lines = (
            old_string.count("\n")
            + 1
        )
        new_lines = (
            new_string.count("\n")
            + 1
        )

        return ok(
            f"Applied edit to {path}: "
            f"{old_lines} lines -> "
            f"{new_lines} lines",
            changed_files=[path],
        )
```

## 13. 回头看 Write 和 Edit

这一章增加了两个文件工具。Write 和 Edit 代表两种不同的承诺。

```text
Write：
我知道这个文件最终完整地应该长什么样。

Edit：
我知道现有文件中的这一小段，应该变成什么。
```

这个差别会一直影响 Agent 怎样选择工具、承担多大的责任，以及系统应该给它加多强的保护。

### 工具接口会改变模型需要负责的范围

假如 Whale CLI 只有 Write，让它修改一行代码，模型也必须重新生成整个文件。任务从”正确修改一行”扩大成了”正确修改一行，同时准确复现其余所有行”，那些本来不需要改变的内容，也变成了模型必须负责的部分。加入 Edit 后，模型只需要准确描述局部差异，其余内容由程序从当前文件中原样保留。有了 Edit，”其他内容不能动”这件事由工具保证，不再靠模型自觉。

```text
Write：
未修改的内容也依赖模型重新生成

Edit：
未匹配到的内容由程序保证不变
```

工具接口会重新分配模型和程序各自负责什么。

---

### 没改的部分也不能动

生成一份新文章时，我们通常只关心新内容写得好不好。修改已有代码时，要求多了一层：目标位置要改对，其他位置还必须保持原样。后半句更容易出事。一段局部修改即使实现了预期效果，只要顺手删掉一个 import、改乱一段注释，整个任务仍然是失败的。所以文件编辑工具要同时保证两件事：想要的新内容出现了，没有授权修改的内容保持不变。Edit 通过缩小修改范围来降低验证难度，修改范围越小，系统越容易判断这次操作有没有越界。

---

### 查找目标可以宽松，真正修改必须严格

Edit 失败时，我们使用相似度匹配，寻找文件中可能相关的代码：

```text
模型提交：
return `core:${ref.executorId}`;

当前文件：
return `core.${ref.executorId}`;
```

相似度算法可以告诉模型：

> 你可能记错了，文件里有一段很像的内容。

但它不能直接替模型决定：

> 那我就把这一段改掉。

寻找候选位置，可以允许近似和猜测；真正写入文件，必须要求目标精确且唯一。搜索错了，最多多看一段无关内容；修改错了，磁盘上的代码会真的变化。因此同一套系统中，读操作和查找操作可以更宽松，写操作则应该更保守。Glob、Grep 和 Bash 也是同样的分界。

---

### 零匹配、一次匹配和多次匹配是三种不同的状态

`old_string` 的匹配次数反映了模型当前掌握的信息是否足够。

```text
0 次匹配
模型记错了内容，或者文件已经发生变化

1 次匹配
模型描述的目标足够明确

多次匹配
模型找到了某类代码，但还没有说清楚具体是哪一处
```

因此 Edit 的校验是在判断模型目前拥有的证据是否足以授权一次文件修改。零次匹配时，工具应该把当前真实内容返回一些，让模型更新认识；多次匹配时，工具应该告诉模型候选位置，让它补充更多上下文；一次匹配时，才真正落盘。Edit 的返回值构成了一套恢复协议：

```mermaid
flowchart LR
    A["当前信息不足"] --> B["工具指出不足在哪里"] --> C["模型重新 Read 或补充上下文"] --> D["再次提交更准确的修改"]
    D -.-> A
```

失败不会终止 Agent Loop，模型可以根据返回的信息重新尝试。

---

### Read 和 Edit 应该一起设计

Read 返回什么格式，会直接影响 Edit 是否好用。

如果 Read 只给模型一段脱离位置的代码：

```python
return label
```

模型很难判断它来自哪个函数，也很容易构造出多处匹配的 `old_string`。如果 Read 同时返回文件路径、行号、当前范围和周围代码，模型就能理解位置，并从结果中复制一段足够具体的内容交给 Edit。不过行号主要用于理解和导航，真正修改时仍然使用文件中的内容作为锚点。文件前面插入几行后行号会变化，而代码片段只要仍然存在就依然能够定位。Read 的输出同时在为后续 Edit 准备可用的定位材料。

---

### 修改范围越大，系统需要的保护越强

Read 不改变磁盘，风险较低。Edit 修改一个唯一片段。Write 可以替换整个文件。后面的 Bash 甚至可以删除目录、安装依赖或修改 Git 状态。

```text
Read
只观察环境

Edit
改变局部状态

Write
替换整个文件状态

Bash
可能改变整个工作环境
```

能力范围越大，误操作造成的影响也越大，因此保护机制也会逐步增加：

```text
唯一匹配
原子写入
覆盖确认
read-before-write
文件版本检查
人工审批
沙箱隔离
```

工具提供的自由度应该与当前能验证的确定性相匹配。


## 14. 如果不给路径

到这里，每个任务我们都直接告诉了 Whale CLI 文件在哪。但真实场景下不会这样说：

```text
找到格式化执行器引用的地方，把分隔符从冒号改成斜杠。
```

没有路径，只有意图。Read 需要路径才能读，Edit 需要路径才能改——两万五千个文件里，目标藏在哪一个？

下一章加两种搜索：Glob 按文件名缩小范围，Grep 按内容定位关键词。Whale CLI 从此不再等人指路。
