# 第 5 章 · 搜文件：Glob 与 Grep

> 本章代码：`code/chapter-05/`。运行示例：`python ../code/chapter-05/main.py "在 TypeScript 文件中搜索 formatToolExecutorRef 函数的定义，然后把冒号分隔符改成斜杠"`。本章新增 Glob（路径搜索）和 Grep（内容搜索）两个工具。

前四章里，每个任务都是我们直接告诉 Whale CLI 文件路径："读 `src/tools/execution.ts`，改里面的分隔符。"它就能完成。但面对 OpenClaw 这种大型项目，真实的使用场景不是这样的。更可能的说法是："找到格式化工具执行器引用的代码，把分隔符从冒号改成斜杠。"模型知道自己要改什么，却不知道代码在哪个文件里。

现在 Whale CLI 手里的工具都需要一个明确的 `path` 参数。Read 需要路径才能读，Edit 需要路径才能改。没有路径，模型只能根据训练时见过的项目惯例去猜——`src/main.py`？`src/index.ts`？猜错了就是一次无效的工具调用和一条 `Error: 文件不存在` 的返回。在一个陌生仓库里，这种盲猜可能要重复很多次。

模型缺的是在读和改之前先缩小范围的能力。加入 Glob 和 Grep 之后，它可以自己在项目中定位目标。

---

## 1. Read 能读文件，但不知道该读哪一个

把当前版本的 Whale CLI 放进一个陌生代码仓库，然后交给它一个任务："找到用户消息进入系统后的处理路径，从入口追到最终生成回复的位置。"

假设这个仓库有几千甚至上万个文件。模型此前没有看过目录结构，也不知道入口文件叫什么。它只能根据训练中见过的项目惯例猜测：

```text
src/main.py
src/app.py
src/index.ts
src/server.ts
src/gateway.ts
```

猜中时，它能继续向下追。猜错时，`read_file` 返回：

```text
Error: 文件不存在：src/main.py
```

模型再猜下一个。即使路径存在，文件也可能与任务毫无关系。模型读取两百行代码，发现没有消息处理逻辑，再换一个文件。

Read 的职责是给定路径、返回内容，它没有回答另一个问题：几千个文件中，哪些文件值得读？代码仓库不适合从第一个文件开始逐个阅读，Agent 需要在真正读取以前，先缩小搜索范围。

我们用 OpenClaw（2 万多个 TypeScript 文件）真实跑了三次对照。同一个模型（DeepSeek v4-flash），同一个任务：

```text
找到 formatToolExecutionErrorMessage 函数的定义，
告诉我它在哪个文件的第几行。
```

**只有 Read 时**（ch01 的代码快照，10 轮）：

```text
⏺ read_file(package.json)                          ← 先看项目信息
⏺ read_file(src/plugin-sdk/tool-results.ts)        ← 猜路径
⏺ read_file(src/agents/tools/tool-results.ts)      ← 再猜
⏺ read_file(src/agents/runtime/index.ts)           ← 继续猜
⏺ read_file(packages/agent-core/src/agent-loop.ts) ← 猜到别的包里
⏺ read_file(packages/agent-core/src/errors.ts)     ← 越猜越远
Error: 达到最大轮数 10，任务仍未完成
```

模型一直在猜路径，每个名字都看似合理——`tool-results.ts`、`errors.ts`——但就是不包含目标函数。

**加了 list_dir + Read 后**（ch02 的代码快照，10 轮）：

```text
⏺ list_dir(.)                    ← 看根目录，48 个条目
⏺ list_dir(src)                  ← 116 个子目录
⏺ list_dir(src/tools)            ← 只有 types.ts
⏺ list_dir(src/utils)            ← 51 个文件，没有目标
⏺ list_dir(src/llm)              ← 不相关
⏺ read_file(src/tools/types.ts)  ← 不是目标
⏺ list_dir(packages)             ← 翻到 packages
⏺ list_dir(packages/ai/src)      ← 越翻越远
Error: 达到最大轮数 10，任务仍未完成
```

不再盲猜了，但换成了另一种低效操作——逐目录翻阅。2 万多个文件分散在几百个目录里，list_dir 一次只能看一层，10 轮根本翻不完。

**加了 Grep 后**（ch05 的代码快照，1 轮）：

```text
⏺ grep(pattern=”formatToolExecutionErrorMessage”)
  ⎿ src/agents/tool-result-error.ts:127:export function formatToolExecutionErrorMessage(...)
    ... (9 处引用)
```

1 轮，直接定位到 `src/agents/tool-result-error.ts` 第 127 行。

| | 只有 Read | Read + list_dir | Read + list_dir + Grep |
|---|---|---|---|
| 工具调用次数 | 10 | 10 | 1 |
| 任务结果 | 失败 | 失败 | 成功 |

三次测试用的是同一个模型，唯一的变量是工具。Read 猜路径，list_dir 翻目录，Grep 直接搜内容——差距不是效率问题，是能不能完成任务的区别。

## 2. 文件名线索和代码线索，需要两种搜索方式

模型寻找代码时，手里的线索并不总是一样。

有时我们知道文件大概长什么样：

```text
找到项目里的所有测试文件。
寻找 src 目录下的 TypeScript 文件。
查找名字中包含 config 的文件。
```

这些线索都指向文件路径或文件名，适合使用 Glob。

有时我们知道代码里可能出现什么：

```text
dispatchInboundMessage 在哪里定义？
哪些地方还在使用旧配置名 MAX_RETRIES？
错误文本 “database is locked” 是从哪里抛出的？
```

这些线索指向文件内容，适合使用 Grep。

两者回答的问题不同：Glob 问的是"哪些文件的路径符合这个模式"，Grep 问的是"哪些文件的内容包含这个关键词或正则"。所以没有固定的"先 Glob，再 Grep"流程，模型根据当前线索选择工具。

| 手里的线索 | 适合的工具 |
| --- | --- |
| 已经知道准确路径 | 直接 Read |
| 知道文件名、扩展名或目录范围 | Glob |
| 知道函数名、变量名或错误文本 | Grep |
| 只知道模糊的业务目标 | 先查看目录，或尝试几个候选关键词 |

具体用哪个，看手里有什么线索。

## 3. Glob：按路径模式筛选候选文件

先看一个具体任务："找到项目中所有测试文件。"

我们不关心文件内容，只关心路径。一个常见项目可能长这样：

```text
openclaw/
├── README.md
├── package.json
├── src/
│   ├── tools/
│   │   ├── execution.ts
│   │   ├── availability.ts
│   │   ├── planner.ts
│   │   └── types.ts
│   ├── gateway/
│   └── sessions/
├── test/
│   └── e2e/
└── packages/
    ├── sdk/
    └── gateway-protocol/
```

Glob 使用路径模式进行匹配，几个常见符号：

```text
*
匹配当前这一层中的任意字符

?
匹配一个字符

**
跨目录递归匹配
```

例如：

```text
*.ts
当前目录下的 TypeScript 文件

src/tools/*.ts
src/tools 目录下一层中的 TypeScript 文件

src/**/*.test.ts
src 下任意目录中的测试文件

src/tools/**/*.ts
src/tools 下所有层级中的 TypeScript 文件
```

模型调用：

```json
{
  "name": "glob",
  "arguments": {
    "pattern": "src/**/*.test.ts",
    "path": "."
  }
}
```

返回：

```text
src/tools/availability.test.ts
src/tools/boundary.test.ts
src/tools/planner.test.ts
```

Glob 不打开文件，也不关心这些文件里面写了什么。它只利用路径结构，把原本可能有几千个文件的仓库缩小成几个候选文件。所以 Glob 的返回值只需要文件路径。如果它顺便把每个文件的内容也返回，搜索工具又会退化成一次大规模 Read。

## 4. Grep：在文件内容中定位关键词

Glob 能找到测试文件，却回答不了"函数 `formatToolExecutorRef` 在哪里定义"。文件名中未必包含 `formatToolExecutorRef`，这时要搜索文件内容。

Grep 接收一个关键词或正则表达式，逐个检查文件中的文本：

```json
{
  "name": "grep",
  "arguments": {
    "pattern": "formatToolExecutorRef",
    "path": ".",
    "glob": "**/*.ts"
  }
}
```

返回：

```text
src/tools/execution.ts:11:export function formatToolExecutorRef(ref: ToolExecutorRef): string {
src/tools/index.ts:10:export { formatToolExecutorRef } from "./execution.js";
src/tools/planner.test.ts:6:import { formatToolExecutorRef } from "./execution.js";
```

每一条结果的格式是：

```text
文件路径 : 行号 : 匹配行内容
```

这个格式正好给下一步 Read 提供参数：

| Grep 返回的字段 | 对应 Read 的参数 |
| --- | --- |
| `src/tools/execution.ts` | `path` |
| `11` | `start_line` 附近 |

模型可以继续调用：

```json
{
  "name": "read_file",
  "arguments": {
    "path": "src/tools/execution.ts",
    "start_line": 1,
    "end_line": 27
  }
}
```

Grep 没有直接返回整个文件，它只告诉模型：

> 你要找的内容，可能在这些位置。

---


<WhaleInsight>

Grep 找到关键词在哪，但上下文不够。模型需要看到那行代码的前后才能理解含义。所以 Grep 是"缩小范围"，Read 是"看清细节"——两步缺一不可。

</WhaleInsight>

## 5. 为什么 Grep 命中以后还要再 Read

Grep 已经返回了这一行：

```text
src/tools/execution.ts:11:
  export function formatToolExecutorRef(
    ref: ToolExecutorRef): string {
```

模型为什么不直接 Edit？因为一条匹配行通常缺少足够的上下文，模型还不知道：

* 这个函数前面有哪些 import；
* 函数体有多少行；
* 分隔符在哪些 case 分支中使用；
* 同名函数是否处于条件分支中；
* 修改会不会影响其他逻辑；
* 构造怎样的 `old_string` 才能唯一匹配。

再看另一个结果：

```text
src/tools/execution.ts:14:      return `core:${ref.executorId}`;
```

虽然已经接近目标，但直接用这一行调用 Edit，也可能匹配到其他 case 分支中的相似格式。更稳妥的过程是：

```mermaid
flowchart LR
    A["Grep 找到候选位置"] --> B["Read 读取前后几十行"] --> C["模型理解 函数边界"] --> D["Edit 精确替换"]
```

搜索结果的作用是定位，Read 的作用是补充上下文，Edit 的作用是执行确定的局部修改。这些工具各自返回的信息，都在为下一步准备参数。

## 6. 用 Python 实现最小的 Glob 和 Grep

先不考虑性能和大型仓库，只做一个能够运行的版本。

### Glob 的最小实现

```python
class GlobTool(Tool):
    name = "glob"
    description = "按文件名模式搜索文件路径。"
    schema = {
        "type": "function",
        "function": {
            "name": "glob",
            "description": "按文件名模式搜索文件路径。",
            "parameters": {
                "type": "object",
                "properties": {
                    "pattern": {"type": "string"},
                    "path": {"type": "string"},
                },
                "required": ["pattern"],
            },
        },
    }

    def __call__(
        self, *, pattern: str, path: str = "."
    ) -> str:
        root = Path(path).resolve()

        if not root.exists():
            return f"Error: 路径不存在：{path}"

        if not root.is_dir():
            return f"Error: {path} 不是目录"

        matches = []

        for file_path in sorted(root.glob(pattern)):
            if file_path.is_file():
                matches.append(
                    str(file_path.relative_to(root))
                )

        if not matches:
            return f"没有文件匹配模式：{pattern}"

        return "\n".join(matches)
```

### Grep 的最小实现

```python
class GrepTool(Tool):
    name = "grep"
    description = "用正则表达式搜索文件内容。"
    schema = {
        "type": "function",
        "function": {
            "name": "grep",
            "description": "用正则表达式搜索文件内容。",
            "parameters": {
                "type": "object",
                "properties": {
                    "pattern": {"type": "string"},
                    "path": {"type": "string"},
                    "glob": {"type": "string"},
                },
                "required": ["pattern"],
            },
        },
    }

    def __call__(
        self,
        *,
        pattern: str,
        path: str = ".",
        glob: str = "**/*",
    ) -> str:
        root = Path(path).resolve()

        if not root.exists():
            return f"Error: 路径不存在：{path}"

        try:
            regex = re.compile(pattern)
        except re.error as exc:
            return (
                f"Error: 正则表达式无效：{exc}"
            )

        matches = []

        for file_path in sorted(
            root.glob(glob)
        ):
            if not file_path.is_file():
                continue

            try:
                text = file_path.read_text(
                    encoding="utf-8"
                )
            except (
                UnicodeDecodeError,
                PermissionError,
                OSError,
            ):
                continue

            for line_no, line in enumerate(
                text.splitlines(),
                start=1,
            ):
                if regex.search(line):
                    relative = file_path.relative_to(
                        root
                    )
                    matches.append(
                        f"{relative}:{line_no}:"
                        f"{line.rstrip()}"
                    )

        if not matches:
            return "没有匹配结果"

        return "\n".join(matches)
```

这个版本已经能处理小项目：

```text
⏺ glob({
     "pattern": "src/tools/**/*.ts",
     "path": "."
   })
  ⎿ src/tools/availability.ts
    src/tools/execution.ts
    src/tools/index.ts
    src/tools/planner.ts
    src/tools/types.ts
```

```text
⏺ grep({
     "pattern": "formatToolExecutorRef",
     "path": ".",
     "glob": "**/*.ts"
   })
  ⎿ src/tools/execution.ts:11:export function formatToolExecutorRef(ref: ToolExecutorRef): string {
    src/tools/index.ts:10:export { formatToolExecutorRef } from "./execution.js";
```

把它放进真实仓库后，新的问题很快出现。

## 7. 真实仓库里的第一个问题：依赖目录淹没结果

将 Glob 放进一个前端项目：

```json
{
  "pattern": "**/*.js",
  "path": "."
}
```

它可能返回大量依赖文件：

```text
node_modules/react/index.js
node_modules/react-dom/index.js
node_modules/@babel/core/lib/index.js
node_modules/eslint/lib/api.js
...
src/App.js
src/index.js
```

我们真正关心的是 `src/` 下的代码，但 `node_modules/`、构建产物和缓存目录中的文件，数量往往远多于项目自己的源文件。Grep 也一样。搜索 `useState`，依赖库的实现、打包文件和类型声明可能占了大部分结果，项目代码反而埋在后面。最朴素的处理是维护一组默认忽略目录：

```python
IGNORE_DIRS = {
    ".git",
    ".venv",
    "__pycache__",
    "node_modules",
    "dist",
    "build",
    ".pytest_cache",
    ".mypy_cache",
}
```

判断路径是否经过这些目录：

```python
def should_ignore(
    file_path: Path,
    root: Path,
) -> bool:
    relative = file_path.relative_to(root)

    return any(
        part in IGNORE_DIRS
        for part in relative.parts
    )
```

Glob 和 Grep 遍历时跳过：

```python
if should_ignore(file_path, root):
    continue
```

同一个查询现在只返回项目自己的文件：

```text
src/App.js
src/index.js
src/utils/api.js
```

但手写忽略列表也有局限——每个项目忽略的目录不同，仓库已经通过 `.gitignore` 写明哪些内容不属于源码搜索范围，工具最好能够直接使用这份规则，而不是重新维护一套近似版本。这个问题会成为后面引入 Ripgrep 的一个重要原因。

## 8. 真实仓库里的第二个问题：搜索结果挤满上下文

过滤掉依赖目录后，搜索结果仍然可能很多。比如搜索：

```text
TODO
```

一个大型仓库中可能有几百甚至几千处匹配。如果 Grep 把所有结果一次性返回，搜索工具本身就会占满上下文。跟第 3 章 Read 一样，能返回全部，不等于应该一次返回全部。

先给结果设置全局上限：

```python
MAX_GLOB_RESULTS = 500
MAX_GREP_RESULTS = 200
```

达到上限后停止，并明确告诉模型结果被截断：

```text
显示前 200 条匹配。
还有更多结果，请缩小 path、glob 或 pattern。
```

不能只截断而不说明，否则模型会误以为自己已经看到了全部匹配。Grep 还可以提供不同的输出模式。

### 只返回文件名

```text
files_with_matches
```

适合先确认哪些文件相关：

```text
src/tools/execution.ts
src/tools/planner.test.ts
```

### 返回匹配内容

```text
content
```

适合继续查看具体行：

```text
src/tools/execution.ts:14:      return `core:${ref.executorId}`;
src/tools/planner.test.ts:132:    ).toBe("plugin:demo:plugin_tool");
```

### 返回每个文件的匹配数量

```text
count
```

适合判断某个关键词主要集中在哪里：

```text
src/tools/execution.ts:4
src/tools/planner.test.ts:2
```

这些输出模式控制的是搜索结果向上下文中注入多少信息。模型目前只需要候选文件时，返回完整匹配行就是多余的。

## 9. Python 搜索能用，为什么还要换成 Ripgrep

当前 Python 实现已经正确工作，但它搜索一个仓库时，需要遍历文件、逐个打开、读取文本、逐行运行正则，文件越多，重复的文件系统操作越多。而代码搜索是编辑器和开发工具反复优化过的问题，早期可以使用：

```bash
grep -R
```

后来出现了更适合代码仓库的搜索工具，它们开始处理：

* 递归目录；
* 忽略版本控制和依赖文件；
* 跳过二进制；
* 并行扫描；
* 更快的正则匹配；
* 统一的路径与行号输出。

Ripgrep，也就是 `rg`，把这些能力组合在了一起，一个命令就可以搜索代码：

```bash
rg "formatToolExecutorRef" .
```

输出：

```text
src/tools/execution.ts:11:export function formatToolExecutorRef(ref: ToolExecutorRef): string {
src/tools/index.ts:10:export { formatToolExecutorRef } from "./execution.js";
```

它默认会读取 `.gitignore`，避免搜索仓库已经排除的依赖、缓存和构建结果，也会自动跳过大部分二进制文件，不需要在 Python 中重新实现一整套代码搜索器，Whale CLI 可以直接把 Ripgrep 当搜索后端。

## 10. 保持工具接口不变，把底层换成 Ripgrep

模型仍然调用：

```json
{
  "name": "grep",
  "arguments": {
    "pattern": "formatToolExecutorRef",
    "path": ".",
    "glob": "**/*.ts"
  }
}
```

模型不需要知道底层是 Python 逐文件扫描还是 Ripgrep，工具接口保持不变，只替换内部实现。

```python
import shutil
import subprocess


def grep_with_ripgrep(
    pattern: str,
    path: str,
    glob_pattern: str | None,
    case_insensitive: bool,
) -> str | None:
    rg = shutil.which("rg")

    if rg is None:
        return None

    command = [
        rg,
        "--no-heading",
        "--line-number",
        "--color=never",
    ]

    if case_insensitive:
        command.append("--ignore-case")

    if glob_pattern:
        command.extend([
            "--glob",
            glob_pattern,
        ])

    command.extend([
        pattern,
        path,
    ])

    try:
        result = subprocess.run(
            command,
            capture_output=True,
            text=True,
            timeout=20,
        )
    except subprocess.TimeoutExpired:
        return (
            "Error: 搜索超过 20 秒。"
            "请缩小搜索目录、文件类型或关键词范围。"
        )

    if result.returncode == 0:
        return result.stdout

    if result.returncode == 1:
        return "没有匹配结果"

    return None
```

Ripgrep 的退出码有特殊含义：

```text
0
找到了匹配

1
没有匹配，这是正常结果

其他值
命令执行发生错误
```

`--no-heading` 让每一条结果都带文件路径，`--line-number` 加入行号，`--color=never` 去掉终端颜色控制字符，避免模型收到 ANSI 转义码。如果系统中没有安装 `rg`，回退到刚才的 Python 实现：

```python
# GrepTool.__call__ 内部
result = grep_with_ripgrep(...)

if result is not None:
    # 截断到 MAX_GREP_RESULTS 条并提示
    return result

return grep_with_python(...)
```

两种后端必须返回相同格式：

```text
path:line_number:content
```

底层实现变了，模型的后续行为不需要改变。但有一个坑——Ripgrep 提供：

```text
--max-count N
```

看起来像”最多返回 N 条结果”，实际上它限制的是每个文件最多返回 N 条。如果有一百个文件，每个文件都允许返回两百条，结果仍然可能非常大，因此全局结果上限仍然应该在 Whale CLI 这一层处理，而不是完全依赖 `--max-count`。

用外部二进制还是纯语言实现？这个选择各家都做了：

理想化的搜索过程看起来像这样：

提出任务，模型马上想到正确关键词，Grep 一次命中，Read，Edit。

真实任务通常没有这么顺。例如追踪陌生仓库中的消息处理链路，模型一开始可能只知道几个很宽泛的词：

```text
message
chat
dispatch
handler
```

第一次 Grep 返回大量结果。模型看到目录和函数名以后，缩小范围——先把 path 限制到 `src/gateway`，再搜索 `dispatch`。仍然不够准确时，它可能 Read 某个候选文件，Read 结果中出现一个更具体的符号 `dispatchInboundMessage`，下一轮 Grep 就可以直接搜索这个函数名。因此，一次搜索任务常常是：

```mermaid
flowchart LR
    A["宽泛关键词"] --> B["获得目录 文件名"]
    B --> C["缩小 path 或 glob"]
    C --> D["更具体的 标识符"]
    D --> E["Read 候选位置"]
    E --> F["发现新的 搜索线索"]
    F -.-> C
```

搜索词不是预先写死的，上一轮工具结果会成为下一轮搜索参数的来源。模型不必一开始就知道完整路径，可以通过多轮搜索逐步逼近目标。

## 12. 一次完整的 Glob、Grep、Read、Edit 过程

用本章的代码跑一次完整流程：

```bash
python ../code/chapter-05/main.py "找到 formatToolExecutorRef 函数的定义，把 JSDoc 注释从 compact diagnostic label 改成 human-readable diagnostic label，再把上面那段注释里的 diagnostics/logging 改成 diagnostics, logging, and UI display"
```

v4-flash 的输出（1 次 Grep + 1 次 Read + 2 次 Edit + 1 次验证 Read）。模型手头有明确的函数名，直接用 Grep 搜索：

```text
⏺ grep({"pattern": "formatToolExecutorRef"})
  ⎿ src/tools/execution.ts:11:export function formatToolExecutorRef(ref: ToolExecutorRef): string {
    src/tools/index.ts:10:export { formatToolExecutorRef } from "./execution.js";
    src/tools/planner.test.ts:6:import { formatToolExecutorRef } from "./execution.js";
```

一条 Grep 定位到了定义在 `execution.ts` 第 11 行，还顺带看到了哪些文件引用了它。模型接着读取完整文件：

```text
⏺ read_file({"path": "src/tools/execution.ts"})
  ⎿ # src/tools/execution.ts (26 lines, showing 1-26)
      1  // Defines tool execution references used by the runtime dispatcher.
      ...
      8   * diagnostics/logging and must not become a parser contract.
     10  /** Render an executor ref as a compact diagnostic label. */
```

看到两处注释需要修改，模型根据 Read 的真实内容构造 Edit：

```text
⏺ edit_file({
     "old_string": " * diagnostics/logging and must not become a parser contract.",
     "new_string": " * diagnostics, logging, and UI display and must not become a parser contract."
   })
  ⎿ Applied edit to src/tools/execution.ts: 1 lines -> 1 lines

⏺ edit_file({
     "old_string": "/** Render an executor ref as a compact diagnostic label. */",
     "new_string": "/** Render an executor ref as a human-readable diagnostic label. */"
   })
  ⎿ Applied edit to src/tools/execution.ts: 1 lines -> 1 lines
```

模型最后又 Read 了一次文件确认修改生效。整条链路是：

- Grep：用函数名直接定位定义位置
- Read：读取匹配文件的完整上下文
- Edit x2：逐个替换注释内容
- Read：验证修改结果

注意模型跳过了 Glob。它手里已经有明确的函数名，不需要先按文件类型筛选。这不是主程序硬编码的顺序——如果只说"找到格式化相关的代码"而没给出函数名，模型可能会先用 Glob 缩小范围再 Grep。每一个工具的结果都能成为下一步的输入。

## 13. 搜索工具的几个设计取舍

Glob 和 Grep 加进来之后，Agent 获取上下文的方式变了。

Grep 的输出格式 `path:line_number:content` 不是随便定的——路径可以直接交给 Read，行号帮模型选择读取范围，匹配内容帮模型判断这个位置值不值得继续看。搜索结果的每一段都在为下一个工具准备输入。

搜索多返回几个无关文件，代价只是上下文；Edit 改错一行，代价是磁盘上的代码真的坏掉。所以 Glob 和 Grep 可以返回多个候选，Edit 要求目标精确且唯一。Bash 也是同样的分界——后面会碰到。

当模型已经知道函数名或错误文本时，Grep 直接命中。但如果只描述"找到负责把消息发回客户端的地方"，而项目中使用的是模型从未见过的内部术语，精确关键词未必一次命中。语义搜索、代码图谱可以补充 Glob 和 Grep，但最终仍然需要 Read 当前磁盘上的真实代码。

## 14. 从散文件到模块

到这一章为止，`tools.py` 已经快 700 行了。五个工具、二进制检测、模糊匹配、忽略目录全挤在一个文件里，找一个函数要翻好几屏。后面还要加 Bash、TodoWrite，再继续往里塞就翻不动了。

`code/chapter-05/full/` 把同样的代码按职责拆开：

```text
full/
├── tools/
│   ├── base.py              ← Tool 基类
│   └── file/

│       ├── write_tool.py
│       ├── edit_tool.py

│       └── grep_tool.py

│   └── toolset.py           ← Toolset 注册表

├── ui/
```

逻辑没有变，每个文件只放一个工具。后面加 Bash 就放 `tools/bash/`，加 Todo 就放 `tools/todo/`。

前面几章一直用 `python main.py "任务"` 来跑，每次只执行一个任务就退出。代码拆成模块以后，可以把它装成一个命令行工具。`full/` 里有一个 `pyproject.toml`：

```toml
[project.scripts]
whale-cli = "ui.shell.main:main"
```

这一行告诉 pip：安装这个包的时候，顺便在系统里注册一个 `whale-cli` 命令，指向 `ui/shell/main.py` 的 `main()` 函数。装完以后不用再记路径，随便在哪个项目目录下敲 `whale-cli` 就能进入交互式对话：

```bash
uv pip install -e .

# 去你想让它操作的项目

```

`ui/shell/main.py` 用 Rich 做了终端输出——工具调用有颜色区分，模型的最终回答用 Panel 包裹，比之前 `print()` 的版本好看不少。这不是重点，重点是现在的代码结构撑得住后面继续加东西了。

## 15. 改完以后，怎么知道对不对

Grep 找到位置，Read 读到上下文，Edit 改了两处注释，每次都返回 `Applied edit`。

但"写进磁盘"不等于"代码正确"。如果 TypeScript 类型定义没同步更新，编译器会直接报错；如果改动破坏了别的测试，测试框架会告诉你哪一行出了问题。这些反馈现在 Whale CLI 收不到，它能看代码、能改代码，却不能让代码跑起来。
